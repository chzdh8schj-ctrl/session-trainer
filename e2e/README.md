# e2e — проверки «Тренажёра к сессии»

Два независимых скрипта на Node 26, без npm-зависимостей: `api-smoke.mjs` (API целиком) и
`ui-check.mjs` (фронт отдаётся и живой). Playwright — необязательное дополнение, см. конец.

Скрипты создают только объекты с префиксом `e2e-` и удаляют их за собой. Реальные предметы,
билеты и расход ИИ не меняются (кроме одного настоящего запроса к DeepSeek, если ключ задан, —
он попадает в `/api/usage`, как обычная генерация).

## Что нужно

- Node 26+ (`node --version`).
- Запущенный backend: `http://127.0.0.1:8010`.
- Пароль сайта из `backend/.env` (`SITE_PASSWORD`).

Запуск backend (в отдельном окне):

```powershell
cd backend
uv run uvicorn app.main:app --host 127.0.0.1 --port 8010
```

## api-smoke.mjs

```powershell
# из корня проекта
$env:SITE_PASSWORD = 'пароль из backend/.env'
node e2e/api-smoke.mjs

# или явно, без env
node e2e/api-smoke.mjs --base-url http://127.0.0.1:8010 --password 'пароль'
```

Параметры: `--base-url` (env `BASE_URL`), `--password` (env `PASSWORD` или `SITE_PASSWORD`),
`--timeout` (обычный запрос, мс, по умолчанию 10 000), `--ai-timeout` (запросы с ИИ, мс,
по умолчанию 120 000 — генерация билета ждёт DeepSeek до 60 с).

Что проверяется по шагам:

1. `/api/health` без куки → 200; `/api/subjects` без куки → 401.
2. Неверный пароль → 401, куки нет; верный → 204 + кука `st_session` (HttpOnly); `/api/auth/me` → 200.
3. Создание предмета → 201 и он есть в списке.
4. Создание билета с коротким вопросом: есть части; при `ai_status="ok"` у каждой части
   3–4 варианта, `correct_index` в диапазоне, непустой `note`.
5. Ручная часть: верный вариант → `correct: true`, неверный → `correct: false` и есть `note`.
6. `/api/usage`: числа, лимит, `ai_enabled`, месяц.
7. Экспорт → импорт с `replace: false`: в экспорт попадает только созданный предмет, импорт
   создаёт его копию, счётчики и список растут, билеты и части переносятся.
8. Удаление созданного и импортированного предметов → 204; список возвращается к исходному.

**Успех** — последняя строка `Результат: OK` и код выхода `0`. Предупреждения (`!`) не считаются
падением: это ожидаемое поведение, когда ИИ недоступен.

Коды выхода: `0` — успех (предупреждения допустимы), `1` — есть падения (`✗`), `2` — backend
недоступен или не задан пароль. Если backend не запущен, скрипт печатает
`✗ backend недоступен на http://127.0.0.1:8010` и подсказку, без стектрейса.

### Если ИИ недоступен

`ai_status` может быть `manual` (нет ключа / ИИ выключен), `budget` (лимит) или `error`
(DeepSeek ответил ошибкой). Скрипт печатает статус, ставит предупреждения и продолжает:
строгие проверки вариантов выполняются только при `ok`, а ответы на часть проверяются на
созданной вручную части. Красных `✗` из-за ИИ быть не должно.

### Если что-то упало

- `✗ /api/subjects без куки → 401 — HTTP 200` — дыра в авторизации, бэкенд отдаёт данные без
  сессии (это баг, не проблема теста).
- `✗ вход с верным паролем → 204 — HTTP 401` — пароль не совпадает с `SITE_PASSWORD` в
  `backend/.env`; проверь, что backend перезапущен после правки `.env`.
- `✗ после входа есть кука st_session` — backend не выставляет куку (или `Cookie` не сохраняется).
- `HTTP 500` — смотри лог uvicorn: чаще всего битая БД после ручных правок или исключение в
  `repo.py`. Тест после такого мог оставить `e2e-*` предметы — удали их через интерфейс.
- `HTTP 404` на `/api/...` — backend на другом адресе или старая версия; проверь `--base-url`.

## ui-check.mjs

```powershell
# backend со собранным фронтом (frontend/dist)
node e2e/ui-check.mjs

# vite dev
node e2e/ui-check.mjs --url http://127.0.0.1:5173

# явный адрес (env UI_URL)
node e2e/ui-check.mjs --url http://127.0.0.1:8010
```

Без `--url` проверяются оба адреса: `BASE_URL`/`UI_URL` (по умолчанию 8010) и 5173.
Для каждого адреса: корень отвечает 200, в HTML есть `id="root"`, найден скрипт
(`/assets/*.js` — сборка, `/src/main.tsx` — vite dev), для сборки ассет реально скачивается,
`/login` отдаёт HTML. Печатается длина HTML и режим (сборка или dev).

**Успех** — `Результат: OK` и код `0`, если хотя бы один адрес полностью рабочий.
Коды: `0` — ок, `1` — фронт отвечает, но не как ожидалось (нет `#root`, нет скриптов, нет ассетов),
`2` — фронт недоступен ни на одном адресе.

Собрать фронт для проверки через backend:

```powershell
cd frontend
npm install
npm run build
```

## Playwright (необязательно, не проверено)

`e2e/playwright/` — заготовка одного сценария: логин → добавить предмет → увидеть его.
В этом окружении она **не запускалась**: `npx playwright install chromium` не уложился в
7 минут (скачивание браузера тяжёлое), поэтому основной проверкой остаётся `ui-check.mjs`.
Если браузеры уже стоят:

```powershell
cd e2e/playwright
npm install
npx playwright install chromium   # один раз, ~150 МБ
$env:SITE_PASSWORD = 'пароль'
$env:E2E_BASE_URL = 'http://127.0.0.1:5173'   # или 8010, если фронт собран
npx playwright test
```

Учти: селекторы написаны по текущей вёрстке (`Login.tsx`, `Subjects.tsx`); если тексты кнопок
поменяются, тест нужно поправить. Скрипт удаляет созданный предмет через UI (confirm принимается).

## Данные и безопасность

- Пароль не логируется. Кука хранится только в памяти процесса.
- Импорт делается не полным экспортом (иначе реальные предметы задублировались бы), а срезом
  из одного созданного предмета, `replace: false`.
- Все созданные предметы удаляются в конце, в том числе при падении. Проверка «список
  вернулся к исходному» ловит утечки; если она упала, удали оставшиеся `e2e-*` вручную.
- ИИ: один реальный запрос на билет, если `DEEPSEEK_API_KEY` задан. Расход виден в `/api/usage`.
